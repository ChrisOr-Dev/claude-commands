# /legislate

用一次最強模型的 session，把它的判斷力轉成可長期沿用的 harness 規則——讓之後每一個用較弱模型跑的 session 都因此變強。

---

## 為什麼需要

模型存取權限常常是分層的：最強模型可能只偶爾用得到，日常工作跑在較便宜/較快的模型上。判斷力不會自動在 session 之間傳遞——但檔案會。

`/legislate` 重新定義了高階模型 session 的用法：不是拿來做一次性任務，而是拿來「立法」——寫下規則、派工協議、判斷 rubric，讓明天用的較弱模型能表現得像擁有今天的判斷力一樣。

---

## 如何使用

1. **切換到你能用的最強模型。** 只有在明顯比日常用的模型強時才划算——用同一個等級跑這個指令沒有意義，沒有東西可以「往下立法」。
2. **安裝指令**（見下方 [安裝](#安裝)）。
3. **在 Claude Code 中輸入 `/legislate`**，最好是在你想改善的 repo / config 目錄裡執行。
4. 若被問到，**在開場回答最多 5 個釐清問題**。之後它會自主完成，不需要你再介入。
5. **讓它跑完。** 產出是隨做隨寫的，就算中途要停，落在硬碟上的內容也是可用的。
6. **讀完結尾的一頁總結**後，自己 review 新增/改動的檔案再信任它——當成在 review PR，不是在讀聊天回覆。
7. **讓較弱的模型在下次 session 讀取這些新檔案**——這才是真正的效益所在。

---

## 功能

| 步驟 | 動作 |
|------|------|
| 作業規則 | 自主作業、開場最多問 5 題、隨做隨寫、改檔前先備份、寫給較弱的讀者看 |
| A | **快速診斷** — 目前 harness 最漏 token、最易失焦、最易出錯的前三名 |
| B | **重寫根設定檔** — 槓桿最高、每個 session 都會載入的檔案 |
| C | **模型調度協議** — 派工規則、回報合約、升降級階梯、驗證不自驗 |
| D | **判斷力外化** — 只有強模型才擅長的判斷，寫成附正反例的 rubric |
| E | **派工 prompt 模板** — 搜尋 / 實作 / 重構 / 研究 / 審查各一份的填空模板 |
| F | **維護協議** — 較弱模型如何安全地更新以上所有內容 |
| G | **給未來 session 的信** — 沒被問到但你認為重要的三件事，加上這套制度最可能的退化方式 |
| 收尾 | fresh-context 對抗審查、read-back 驗證、一頁總結、context 快用完時先做收尾再交接 |

## 設計理念

**價值排序、隨做隨寫。** Session 隨時可能中斷——`/last-word` 被中斷不會遺失新東西，但 `/legislate` 被中斷時，槓桿最高的產出應該已經落檔。

**寫給弱讀者看。** 這個指令產出的每一條規則都必須附具體判準和一正一反範例。「保持高品質」不是較弱模型能執行的規則；「同一子任務連錯兩次、帶完整失敗軌跡 → 升級」才是。

**驗證不自驗。** 判斷力外化的核心精神，就是做事的模型不該是給自己打分的模型——即使在這個立法 session 本身，產出也要經過 fresh-context 的對抗審查才算完成。

**誠實面對極限。** 再多的 rubric 也無法讓較弱模型在真正模糊或講品味的決策上變成強模型。`/legislate` 要求明確寫出遇到這種情況該怎麼辦：升級模型、找外部第二意見、或明說做不到。

cp legislate/legislate.md ~/.claude/commands/legislate.md
